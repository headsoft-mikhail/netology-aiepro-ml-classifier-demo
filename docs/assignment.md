## Суть и допуск

Превратить учебный или собственный ИИ-прототип в воспроизводимый пилотный сервис, который другой человек сможет запустить и проверить.

Для допуска: изучить материалы выбранной траектории; получить зачёты по всем обязательным домашним заданиям; выбрать исходный проект модулей 3–7 либо сформулировать собственный. В боковом меню задание допуска уже отображается с зачётом.

## Четыре траектории

| Основная траектория | Предлагаемый исходный проект | Имеющаяся основа |
|---|---|---|
| ML/DL | Классификация обращений пользователей | Датасет, векторизация, модели, метрики, MLflow, notebook, README |
| LLM | Анализ пользовательских запросов | API модели, system prompt, структурированный вывод, пайплайн, базовая проверка |
| RAG | Корпоративный Q&A-ассистент | База знаний, chunking, embeddings, vector store, retrieval, генерация, тестовые вопросы |
| ИИ-агенты | Агент поддержки инженера | LLM, tools/functions, memory, сценарии, обработка ошибок, подключённый RAG |

Разрешено совмещать траектории, но одна должна быть основной; дополнительные компоненты не заменяют её обязательные требования.

Собственный проект допустим при понятной бизнес-задаче, соответствии хотя бы одной траектории, выполнимом объёме, зафиксированном исходном прототипе или минимальном рабочем baseline и законном доступе к данным/моделям. **Траекторию и объём собственного проекта требуется согласовать с экспертом в первую неделю.**

## Сроки

- Работа: 4 календарные недели; на странице старта указано 28 дней после нажатия кнопки.
- Ориентир активного времени: 1080 минут, то есть 18 часов. Это ориентир курса, не гарантия трудозатрат на новый проект.
- Проверка экспертом: до 14 рабочих дней после загрузки.
- Доработка после проверки: до 7 рабочих дней.

## Этапы

1. Зафиксировать исходную версию и бизнес-задачу.
2. Определить требования и доработать ИИ-компонент.
3. Собрать, протестировать и развернуть сервис.
4. Оформить документацию, демонстрацию и портфолио.

Паспорт проекта: бизнес-задача и польза; целевой пользователь и его сценарий; входы, выходы и ограничения; описание и результаты baseline; цель развития и основная траектория.

После baseline нужна таблица требований: для каждого функционального требования, требования качества и безопасности — измеримый критерий и способ проверки. Примеры: формат ответа API; F1/доля валидных ответов/качество поиска/задержка; отсутствие секретов и персональных данных, безопасные ошибки.

## Общие требования к сервису

- HTTP endpoint основного сценария и `GET /health`. Вызов API внешней модели не считается собственным API сервиса.
- Сервисный слой и API находятся вне notebook. Notebook допустим для EDA и экспериментов.
- Параметры модели/пайплайна, пороги и пути вынесены в YAML, JSON или переменные окружения. Примеры в задании: модель, температура, top_k, chunk size.
- `.env.example` без реальных секретов.
- Обработка некорректного ввода, недоступности внешнего сервиса и внутренних ошибок обработки. Для полностью локального проекта следует явно описать применимость внешних зависимостей.
- Логирование ключевых событий без секретов и персональных данных.
- Минимум три контрольных сценария; автоматические тесты минимум одного компонента.
- Запуск по инструкции в выбранной среде и контрольная проверка.
- Доработка ИИ-компонента с подтверждённым сравнением «до/после».

## Дополнительные артефакты

- **ML/DL:** сохранённая модель и эксперименты MLflow.
- **LLM:** журнал проверочных запросов, сравнение моделей или промптов.
- **RAG:** документы базы знаний и таблица тестовых вопросов.
- **ИИ-агенты:** конфигурация tools, memory и RAG, протокол минимум восьми сценариев.

Отдельного обязательного шаблона программного проекта нет. Эксперт должен последовательно проверить baseline, требования, изменения ИИ-компонента, сервис, тесты и результаты.

Перечисленные инструменты: Python 3.10+, Git, GitHub/GitVerse, FastAPI/Flask, опционально Streamlit/Gradio, Docker/compose, pytest или аналог, MLflow для ML/DL, Chroma/Qdrant для RAG, LangChain/LangGraph либо собственное управление агентом.

## Применение к выбору темы

Нейросеть не обязана превосходить все классические модели: такого условия в тексте нет. Но итоговая версия обязана улучшить baseline минимум по одному заранее выбранному и согласованному критерию без критического ухудшения остальных. Для собственного проекта нужно согласовать основную траекторию и объём с экспертом в первую неделю. Заголовок и метрики ML/DL ориентированы на классификацию: регрессия требует согласования замены метрик и способа разбиения.

## Уточнения из полного задания

### План по неделям

1. Baseline, бизнес-задача, пользователь, сценарий, требования, критерии, архитектура.
2. Улучшение ИИ-компонента, расширение проверочного набора, промежуточный замер.
3. HTTP API, конфигурация, ошибки, логи, автотесты, Dockerfile.
4. Развёртывание и проверка, сравнение, README, презентация, демонстрация, портфолио.

Baseline нужно не только описать, но сохранить код, параметры и данные, запустить и зафиксировать результат. Для всех сравнений обязательны одинаковые данные или сценарии. Требуются целевые значения критериев качества.

### ML/DL: обязательные условия

Обосновать минимум одно направление улучшения: подбор гиперпараметров, feature engineering, работа с дисбалансом, более сильное представление текста.

- Train/validation/test без утечки; зафиксированы random_state и stratify.
- Эксперименты сравниваются через MLflow.
- Модель сохранена и загружается сервисом без обучения на каждом запуске.
- Один и тот же test-набор для baseline и финальной версии.
- Accuracy, precision, recall, F1 macro/weighted и confusion matrix.

### LLM

Возможные доработки: system prompt и few-shot; валидация JSON с повторным запросом; retry/backoff и контролируемый fallback; базовая модерация/post-filter.

Минимум **10 проверочных запросов**. Сравнить валидность ответов, соответствие ожидаемым полям, время ответа и выбранные дополнительные критерии.

### RAG

Возможные доработки: chunk size/overlap; гибридный поиск/re-ranking; prompt для ответа строго по контексту; порог релевантности.

Минимум **10 вопросов**, включающих прямой ответ, ответ по нескольким фрагментам и отсутствие ответа в базе. Сравнить источники и ответы обеих версий.

### ИИ-агенты

Нельзя просто повторить итоговое задание модуля: требуется содержательное развитие. Минимум одно направление: новый предметный инструмент; маршрутизация между специализированными подагентами либо эскалация человеку; ограничение итераций, обработка зацикливания и контролируемая деградация при отказе LLM/RAG/tool.

Минимум **8 сценариев до и после**, включая tools, RAG, memory, отсутствие информации и сбой компонента.

### Общая проверка и развёртывание

Три общих сценария: штатный запрос; граничный/нетипичный; ошибка пользователя или недоступность внешнего компонента. Дополнительно обязательные сценарии траектории. Для каждого — ожидаемый и фактический результат, статус проверки.

Подробное задание прямо требует Dockerfile (compose при необходимости), проверку запуска в чистом окружении. Можно развернуть локально или в облаке. Если облако недоступно по стоимости/доступу, локальный Docker подтвердить коротким видео. При выборе плана следуем этому более конкретному требованию, хотя вводная страница допускает альтернативную воспроизводимую инструкцию.

### Сдача и оценивание

Защита письменная. Отправить репозиторий/архив, ссылку на сервис или подтверждение локального запуска, презентацию, портфолио-описание. Проверить доступ к материалам без авторизации; особенности запуска можно указать в комментарии.

Для зачёта нужны: задача/пользователь/сценарий/ограничения; baseline и таблица проверяемых требований; запуск без недокументированных действий; API/конфигурация/ошибки/логи/автотесты/развёртывание; обязательные требования траектории; подтверждённое улучшение; отсутствие секретов и персональных данных во всех материалах; понятные воспроизводимые README/презентация/демонстрация/портфолио; содержательные выводы.

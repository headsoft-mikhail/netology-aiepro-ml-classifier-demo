# План исследования данных перед обучением

Статус: подготовлен план; EDA не выполнен. Числа, обнаруженные в ранее удалённых материалах, не считаем результатами нового исследования.

Цель — понять, что означает одна запись, какие данные будут доступны сервису, как связаны CLASS и NSP и как честно сравнить классический классификатор с небольшой MLP. На этом этапе не обучаем модели и не строим сервис.

## 1. На какие работы опираемся

- `../ml-pipeline/coffee_ml_pipeline.ipynb`: обзор таблицы, описание типов, сводки числовых и категориальных колонок, явные выводы; позднее — sklearn Pipeline, DummyClassifier, сравнение и MLflow.
- `../netology-aiml-classification/notebook.ipynb`: словарь признаков, объяснение пропусков через процесс возникновения данных, проверка доступности признаков на момент предсказания, распределение классов, исследование качества данных; позднее — сравнение классических моделей и MLP.
- Justfile этих проектов: запуск инструментов через uv и just. Airflow из `ml-pipeline` для EDA не нужен.

Что исправляем при переносе подхода:

1. Количество пропусков — `isna().sum()`, процент — `isna().mean() * 100`. В старых сводках `na_cnt` ошибочно умножался на 100.
2. Не вызываем `dropna()` перед исследованием пропусков: в coffee notebook это скрывает проблему и меняет выборку.
3. Проверяем дубликаты явно по нужным наборам колонок, а не делаем вывод по уникальности времени или ID.
4. Код класса, даже записанный числом, не превращается в непрерывную величину: среднее CLASS и корреляция Pearson между кодами CLASS/NSP не объясняют их связь.
5. Не выбираем модели по test и не используем test для кривых обучения по эпохам. Для этого будет validation.
6. Не подавляем все предупреждения. Не копируем текстовую обработку, TF-IDF и облака слов: здесь другой тип входных данных.

## 2. Организация: один notebook, два этапа

Основной файл: `experiments/notebooks/01_eda.ipynb`. Краткие результаты и решения — `experiments/README.md`. Детальные таблицы и графики сначала остаются в notebook, отдельный генератор отчётов не нужен.

Структура каждого раздела: вопрос → небольшой блок кода → таблица/график → вывод → что это меняет в проекте. Пояснения пишем в Markdown-ячейках; docstrings не добавляем. `print` допустим в notebook; в вынесенных Python-модулях используем модульный `LOGGER_OBJ`.

**Этап A:** разбор исходного файла и технический аудит всего набора. После него вместе решаем вопросы групп, дублей и разбиения.

**Этап B:** после согласования разбиения — подробный EDA train, связь целей и решения о предобработке. Test остаётся закрыт для исследования зависимостей и выбора решений. Проверки отсутствия пересечений между частями допустимы.

Это устраняет противоречие «сначала EDA или сначала split»: сначала нужно понять структуру данных, затем выделить независимые части, затем изучать закономерности на обучающей части.

## 3. Этап A: исходный файл и качество данных

### A1. Происхождение и единица наблюдения

- Указать первоисточник UCI, название набора и описание способа получения измерений и экспертной разметки.
- Сверить сведения с документацией, входящей в оригинальный архив. Отделить подтверждённые факты от предположений.
- Выяснить, что означает строка: пациент, исследование или сегмент исследования; можно ли несколько строк отнести к одному источнику.
- Записать, что сервис получает готовые числовые характеристики КТГ, а не извлекает их из сырого сигнала или изображения.

Результат: короткий паспорт данных и ограничения применимости. Наличие реальных данных само по себе не гарантирует хорошую обобщающую способность модели.

### A2. Открытие оригинального файла

- Вход: `runtime/data/raw/cardiotocography.zip`, полученный через `just fetch_dataset`.
- Посмотреть список файлов архива, листы XLS, расположение заголовков и служебных строк.
- Прочитать нужный XLS из ZIP в памяти через ZipFile/BytesIO и pandas с xlrd. Скачивание остаётся отдельным шагом; исходный ZIP не изменяем.
- Показать первые строки, размер, типы. Проверить, не попали ли пояснения или итоговые строки в таблицу.
- Сохранить исходный номер строки для разбора проблемных записей.

Результат: правильно прочитанная таблица, без молчаливого удаления строк и без подготовленных train/test-файлов.

### A3. Словарь и роли колонок

Таблица: исходное имя → понятное описание → единицы/кодировка → роль → доступность при предсказании.

Отдельно выделить:

- 21 входной признак по документации; сверить реальные имена и смысл, не выбирать все числовые столбцы автоматически.
- `CLASS` и `NSP` как две экспертные целевые метки.
- Идентификаторы, временные границы сегмента, служебные и производные колонки, если они присутствуют.
- Возможные дополнительные представления целей: их тоже нельзя включать во входы.

Истинные CLASS/NSP не подаются модели как признаки. Предсказанный CLASS как промежуточный результат — отдельная архитектура, которую ещё нужно обосновать.

### A4. Техническое качество

- Типы и ошибки преобразования в числа.
- Количество и процент пропусков по колонкам; нули исследовать отдельно от пропусков.
- Допустимые значения целевых меток и неожиданные значения.
- Полностью пустые и служебные строки.
- Точные дубли всей строки; одинаковые 21 признака; одинаковые признаки вместе с обеими метками.
- Для одинаковых признаков с разными метками — отдельная таблица примеров с исходными номерами строк.
- Возможные группы исследования: сколько строк на группу, есть ли пропуски ID. ID файла нельзя автоматически считать ID пациента.

Результат: перечень проблем с количеством строк и примерами. Ничего не удаляем автоматически: сначала объясняем причину и предлагаем правило.

### A5. Обсуждение разбиения — первая точка решения

Предложение: train/validation/test около 60/20/20 и фиксированный seed. Точный способ зависит от результатов A4.

- Если есть обоснованные группы, не разносить одну группу по разным частям.
- Одинаковые входные записи не должны попасть в разные части. Если это конфликтует с группами, определить общее правило группировки до split.
- Проверить достаточность редких классов для обучения и оценки обеих целей. Не перебирать seed ради удобных результатов.
- Если надёжных групп нет, рассмотреть стратифицированное разбиение и явно указать ограничение независимости наблюдений.
- Согласовать обработку дублей, конфликтующих меток и служебных строк.

Только после обсуждения реализовать минимальную подготовку и сохранить индексы/части в `runtime/data/prepared/`. Исходные измерения не масштабировать на всём наборе. Проверить непересечение записей и групп, покрытие строк и воспроизводимость разбиения.

## 4. Этап B: исследование train

### B1. Баланс целей

Для CLASS и NSP: количество, доля, столбчатый график с подписями, редкие категории. Не объединять категории ради баланса без содержательного основания.

Вывод: достаточно ли примеров для каждой задачи, почему accuracy недостаточно, какие метрики понадобятся. Предварительный ориентир — macro-F1 и precision/recall каждого класса; для NSP отдельно важны пропуски патологических случаев и ложные тревоги. Числовые пороги качества определяем позже, а не обещаем заранее.

### B2. Связь CLASS и NSP — ключевой вопрос

1. По документации определить значения десяти паттернов и трёх NSP. Проверить, есть ли явно заданное правило соответствия.
2. На train построить таблицу количеств `CLASS × NSP` и таблицу долей внутри каждого CLASS; визуализировать heatmap.
3. Для каждого CLASS посчитать число встречающихся NSP. Показать строки, противоречащие гипотезе однозначного соответствия.
4. Если противоречий нет, это подтверждает соответствие на train, но не доказывает универсальное медицинское правило.
5. Правило, выведенное из train, зафиксировать и позднее проверить на validation; не исправлять его по test.

Возможные решения:

| Наблюдение | Что рассматриваем дальше |
|---|---|
| Есть подтверждённое однозначное соответствие | Классификатор CLASS и преобразование его вероятностей в NSP; сравнить с прямым NSP-классификатором |
| Соответствие есть только в train | Рассматривать его как гипотезу и проверять устойчивость, не выдавать за клиническое правило |
| Один CLASS имеет несколько NSP | Прямое предсказание NSP; при пользе второй задачи — MLP с общими слоями и двумя выходами |
| CLASS слишком редок или недостаточно понятен | Основная задача NSP, CLASS остаётся предметом исследования, а не обязательной целью обучения |

Обучать все варианты не требуется. Итог EDA — обоснованный выбор одного основного варианта и разумного сравнения. Каскад с обучаемой второй моделью потребует out-of-fold предсказаний первой; пока его не реализуем.

### B3. Распределения входных признаков

- Сводная таблица: count, пропуски, число уникальных значений, min/max, среднее/медиана, std, квантили и IQR.
- Гистограммы всех входных признаков небольшими группами, читаемые подписи и единицы.
- Постоянные/почти постоянные признаки, разные масштабы, асимметрия и накопления нулей.
- Boxplot и доля значений за границами IQR как описательная проверка, не автоматическое правило удаления.
- Экстремальные значения сопоставить с определением признака: необычное значение может быть полезным сигналом, а не ошибкой.

Вывод: какие преобразования стоит проверить при обучении. StandardScaler для линейной модели и MLP обучается только на train. Пока сохраняем исходные значения.

### B4. Связи признаков и различимость классов

- Корреляции входных числовых признаков, при необходимости Pearson и Spearman.
- Выделить сильно связанные пары и проверить, нет ли математически производных колонок.
- Для нескольких понятных признаков сравнить распределения по NSP и, где полезно, CLASS.
- Не удалять признак только за высокую корреляцию и не трактовать отсутствие линейной корреляции как отсутствие полезного сигнала.
- Не вычислять обычную числовую корреляцию с произвольными кодами классов как главный аргумент.

Вывод: гипотезы для будущих моделей; утверждение о хорошем качестве возможно только после честного обучения и оценки.

Ближайшее действие после согласования плана: создать notebook и выполнить только A1–A4, затем обсудить результаты перед разбиением и исследованием train.

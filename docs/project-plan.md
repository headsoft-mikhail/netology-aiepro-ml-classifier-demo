## 1. Цель и границы

Создать воспроизводимый учебный сервис, который классифицирует числовые показатели КТГ и показывает поступающие исследования в порядке предлагаемого приоритета просмотра. Обучить и сравнить классический классификатор и небольшую MLP. Главная учебная цель — понять обучение нейросети, влияние параметров и причины ошибок.

Пользователь — специалист, просматривающий исследования. Гипотеза пользы: при большом списке записей предварительная классификация помогает раньше обратить внимание на потенциально проблемные результаты. Датасет позволяет проверить классификацию, но не подтвердить сокращение времени работы врача или медицинские исходы. Категория записи не равнозначна клинической срочности.

Вход: 21 числовой признак, уже извлечённый из КТГ. Выход: категория normal / suspect / pathologic и вероятности трёх классов. Обработка исходного сигнала, изображений и медицинских документов не входит в проект.

Обязательный объём:
- EDA, контроль качества данных, фиксированное разбиение.
- Классическая модель и MLP, эксперименты в MLflow.
- Зафиксированный baseline и проверяемое улучшение.
- API с выбором модели, минимальный HTML-интерфейс с демопотоком.
- Автотесты, Docker, документация и материалы сдачи.

Опционально после основного объёма: ансамбль вероятностей, загрузка пользовательского CSV. Предлагается демопоток через отдельный producer и брокер Artemis в Docker Compose. Отдельная серверная БД, авторизация, фронтенд-фреймворк, облако, Airflow и обучение на Windows не требуются. Начинаем с CPU на Mac M1 16 GB; возможность MPS рассматриваем только при измеренной необходимости.

## 3. Структура на основе netology-aiagnt

Предложение для согласования: сохраняем подход `netology-aiagnt` — пакет в `src`, модульный `settings.py`, `service/app.py`, `routes.py`, `models.py`, `dependencies.py`, запуск модулей через `__main__.py`, uv и Justfile. Исследования и данные отделены от runtime-сервиса. Каркас создан и опубликован; активен только модуль скачивания.

```text
netology-aiepro-diplom/
├── README.md, Justfile, pyproject.toml, uv.lock
├── .env, Dockerfile, compose.yaml
├── experiments/notebooks/         # исходные исследования
├── experiments/profiles/          # будущие параметры экспериментов
├── src/frontend/                      # HTML, CSS, JS
├── src/classifier/
│   ├── settings.py                  # Настройки проекта
│   ├── data/                     # скачивание и подготовка
│   ├── modeling/                 # модели и эксперименты
│   └── service/                  # API, messaging/, simulator/
├── runtime/                      # всё генерируемое, вне Git
│   ├── data/raw/, prepared/, demo/
│   ├── mlflow/                   # SQLite + artifacts/
│   ├── artifacts/                # выбранные модели
│   ├── reports/                  # audit, графики, выполненные notebooks, тесты
│   ├── logs/, processes/
│   └── jupyter/, ipython/, matplotlib/
├── tests/
└── docs/
```

`experiments/` хранит исследование, а `src/classifier/modeling/` — переиспользуемый код. Notebooks импортируют функции из пакета, а не содержат вторую реализацию обучения. `runtime/mlflow/` хранит историю; `runtime/artifacts/` — только выбранные совместимые версии моделей для API. Frontend физически отделён, но отдаётся FastAPI: отдельный контейнер для статических файлов не нужен.

### Все настройки через pydantic-settings

По примеру `netology-aiagnt/src/ai_agent/service/config.py`: модульные классы `BaseSettings`, `SettingsConfigDict`, префиксы `DATA_`, `TRAIN_`, `MLFLOW_`, `API_`, `BROKER_`, `SIMULATOR_`. Настраиваем пути, seed, splits, гиперпараметры, модель по умолчанию, порты, брокер, интервал поступления и повторные попытки. `.env` содержит настройки без секретов и хранится в Git.

Для серии экспериментов допускаем отдельные профили параметров: загрузка и валидация только через Settings, с документированным приоритетом явных параметров запуска над окружением и defaults. Итоговую конфигурацию каждого запуска сохраняем в MLflow без секретов. Не поддерживаем параллельную независимую систему YAML-настроек. Compose использует те же переменные для портов, volumes и соединений; статические схемы данных не являются настройками.

### Контейнеры и движение данных

```text
producer (service.simulator) → Artemis → service (consumer → inference → SQLite)
                                            ↓
                                     HTTP API → frontend
```

Предлагаемый брокер — Artemis: одна очередь исследований, без кластера. Kafka оставляем альтернативой, если изучение именно Kafka станет отдельной целью; три брокера не реализуем. Официальный Docker-образ описан в [документации Artemis](https://artemis.apache.org/components/artemis/documentation/latest/docker.html). Версию, поддержку архитектуры Mac и совместимый Python-клиент проверим до фиксации зависимостей.

`compose.yaml` запускает `broker`, `service`, `producer` одной командой. Service и producer могут использовать один образ и разные entrypoint. MLflow — отдельный исследовательский сервис/профиль, не обязательная зависимость inference. Модели и демоданные готовы до старта, обучение не запускается автоматически.

Для подтверждения обработки используем небольшую SQLite в runtime volume: записываем результат перед ack. Это не отдельный контейнер БД, а минимальная защита от потери уже подтверждённых записей при перезапуске. Ключ `(session_id, record_id)` предотвращает дубли при повторной доставке. Один процесс API/consumer достаточен для демо. Ошибочные сообщения после ограниченного числа попыток переходят в очередь ошибок; бесконечных повторов нет.

## 4. Данные и EDA

Источник: [UCI Cardiotocography](https://archive.ics.uci.edu/dataset/193/cardiotocography). По описанию источника: 2126 записей, 21 признак, экспертная классификация; лицензия CC BY 4.0. При получении проверяем фактический файл и сохраняем атрибуцию. Это реальные медицинские записи, не синтетически сгенерированные строки: числовые признаки получены автоматической обработкой КТГ, две метки присвоены по согласованным оценкам трёх экспертов-акушеров.

В исходном наборе **две целевые переменные**: `CLASS` — один из 10 морфологических паттернов; `NSP` — normal/suspect/pathologic. Входных измеренных признаков — 21. Обе цели сохраняем в подготовленных данных, но не подаём истинные метки на вход модели. Основной бизнес-выход пока NSP; способ его получения выбираем после исследования связи целей.

### Обязательное исследование связи CLASS и NSP

Рабочая гипотеза пользователя: сначала определить паттерн `CLASS`, затем автоматически получить `NSP`. Проверяем её, а не принимаем заранее как факт.

## 5. Baseline и обучение

### Первые модели

- [ ] DummyClassifier как проверка минимального уровня качества; это вспомогательный ориентир, не единственное содержательное сравнение.
- [ ] Классический baseline: StandardScaler + LogisticRegression; сохраняем единый sklearn Pipeline.
- [ ] Основной baseline улучшения: небольшая PyTorch MLP, начальная архитектура `21 → 32 → 16 → 3`, ReLU, CrossEntropyLoss и Adam.
- [ ] На выходе MLP во время обучения — logits; softmax применяем для ответа с вероятностями.
- [ ] Зафиксировать seed, параметры, split, версии библиотек, код и артефакты baseline.
- [ ] Сохранять train/validation loss и метрики по эпохам, выбирать checkpoint по validation.

Baseline должен быть разумной рабочей моделью, а не намеренно плохой конфигурацией. Сначала фиксируем его train/validation-результаты; test-результаты baseline и финальной версии получаем вместе в конце.

### Небольшая серия экспериментов

Классическая модель: несколько конфигураций силы регуляризации и `class_weight`; при явной необходимости один дополнительный алгоритм, без большого перебора семейств.

MLP: около 4–6 осмысленных экспериментов, преимущественно по одному изменению относительно baseline:
1. Learning rate.
2. Размер скрытых слоёв.
3. Weight decay или небольшой dropout.
4. Веса классов для дисбаланса.
5. Сочетание удачных изменений, если оно обосновано validation.

Правило остановки/выбора checkpoint фиксируем в конфигурации. Финальных кандидатов при необходимости проверяем на нескольких seed на validation, чтобы не принять случайный выигрыш за устойчивое улучшение. Бесконечный поиск параметров не нужен.

Для каждого эксперимента в MLflow сохраняем параметры, seed, версию данных/split, метрики train/validation, графики обучения, checkpoint и краткую гипотезу. В notebook поясняем: что изменили, чего ожидали, что получилось и почему.

### Критерии

Главный кандидат на критерий улучшения — F1 macro. Дополнительно контролируем recall патологического класса и ошибки `pathologic → normal`, а также остальные обязательные метрики. Численные цели и допустимые ухудшения определяем после baseline, до улучшений. Пока значений нет, требование считается незакрытым.

Нейросеть не обязана обойти классическую модель. Нужно показать улучшение зафиксированного baseline по согласованному критерию без критического ухудшения остальных. Если подтверждения не получилось, не скрываем результат и не подбираем по test: анализируем причину и согласуем дальнейшие действия.

## 7. Планируемые команды и пайплайны

Команды ниже — будущий интерфейс `Justfile`; каждая вызывает общий Python-код и читает pydantic-settings. Всё управление — через Justfile.

Основа команд найдена в `netology-aiagnt/Justfile`: `_import_env`, `setup`, `python`, `lock`, `install`, `lint`, `test`, `docker_build`, проверки API и открытие Swagger. При реализации копируем применимые recipes и адаптируем имя пакета, coverage и зависимости. `test` не должен запускать обучение или удалять пользовательские артефакты. `setup` с Homebrew выполняется только явно. Названия mlflow-*/jupyter-* сохранены как в netology-aiml-classification; базовые команды — как в aiagnt.

| `just demo_start / demo_pause / demo_reset` | Управление демосессией | Поток, пауза, явный сброс |

Можно добавить `just pipeline` для последовательности подготовки и baseline. Финальную оценку на test не включаем в автоматически повторяемый цикл экспериментов. Запуск сервиса не запускает обучение или скачивание данных.

Каждый этап проверяет необходимые входы и сообщает понятную ошибку при их отсутствии. Результаты экспериментов имеют отдельные run ID; исходный baseline не перезаписывается. Manifest минимальный: конфигурация, версия данных, seed, количество записей, пути результатов и версия кода при наличии Git.

## 8. API

FastAPI отдаёт API и статическую страницу из одного приложения.

- `GET /health`: процесс работает. Отдельный `/ready` не выдаёт успех при неготовности зависимостей.
- `POST /predict`: объект с именованными 21 признаками и `model = classic | mlp | both`; при реализации ансамбля добавляется `ensemble`.
- Ответ: версия модели, категория и вероятности с явными именами классов. Для `both` — два независимых результата.
- `GET /records`, карточка записи и изменение статуса просмотра; API управления демосессией. `GET /ready` проверяет модели, хранилище и соединение с брокером, `/health` — жизнь процесса.
- Если выбран вариант с CLASS, ответ включает паттерн и способ получения NSP: прямое предсказание или отображение из паттерна.

Проверяем обязательные поля, числовые типы, конечность значений, допустимые категории параметра модели и документированные ограничения входа. Не придумываем медицинские диапазоны: технические и предметные ограничения должны быть обоснованы. Отклонение от обучающего распределения не выдаём автоматически за некорректный ввод.

API не принимает истинную метку для предсказания. Ошибки: некорректный запрос, отсутствующие/несовместимые артефакты, внутренняя ошибка. Внешней модели нет; неприменимость её недоступности описываем. В логах — идентификатор запроса, модель, статус и время, без полного медицинского входа и секретов.

## 9. Интерфейс и демонстрационный поток

### Источник записей

После финальной оценки формируем небольшой фиксированный демонабор из test. Входные признаки и истинные метки сохраняем раздельно. ID исследования и время поступления — демонстрационные. Если специально отбираем примеры разных классов/расхождений, явно это указываем; демонабор не используется для заявления общей метрики качества.

### Работа страницы

1. Пользователь выбирает модель и запускает демосессию через API. Producer получает состояние сессии через внутренний API; это не зависит от открытого браузера.
2. Producer с заданным интервалом публикует запись в Artemis: версия схемы, session_id, record_id, время, выбранная модель и 21 признак. Истинных меток в сообщении нет.
3. Consumer в сервисе проверяет сообщение, выполняет inference и сохраняет ответ. Frontend периодически запрашивает `/records` и отображает уже классифицированные записи. Начинаем с polling; SSE не обязателен.
4. Можно приостановить поток, добавить одну запись вручную кнопкой или сбросить демо.
5. Сортировка переключается между временем поступления и предлагаемым приоритетом: pathologic, suspect, normal; внутри категории — время поступления.
6. По нажатию строки открываются показатели, вероятности и используемая версия модели.
7. «Отметить просмотренным» меняет статус, но не удаляет исследование. Нормальные результаты остаются доступны.
8. Отдельный режим демонстрации показывает истинную метку и сравнение моделей; это не часть информации, доступной модели.

В режиме `both` для сортировки используем явно обозначенную основную модель, вторую показываем для сравнения. Не изобретаем скрытое правило объединения. Модель фиксируется на текущую демосессию; смена требует явного сброса списка, чтобы результаты разных подходов не смешивались незаметно.

Состояние записей и отметки просмотра хранятся в SQLite сервиса; обновление страницы перечитывает список. Явный сброс создаёт новую session_id, старые сообщения не попадают в новую сессию. Producer может повторить сообщение после перезапуска: сервис подавляет дубли по ID. При недоступности брокера/API показываем статус, повторные попытки ограничиваем. Обычный `just down` сохраняет volumes; удаление данных — отдельная явная команда.

## 10. Проверка и запуск

Содержательные автотесты:
- отсутствие target/альтернативной метки во входной схеме, отсутствие пересечения splits;
- соответствие порядка признаков и классов между обучением и inference;
- загрузка артефактов и воспроизводимость предсказания;
- валидный API-запрос, неизвестная модель, отсутствующий признак и некорректное значение;
- вероятности конечны, лежат в [0,1] и суммируются в 1 с допуском;
- повторная доставка не создаёт дубль; ack выполняется после сохранения; ошибочное сообщение не блокирует поток;
- восстановление после перезапуска и изоляция демосессий; корректность CLASS → NSP при выборе этой схемы.

Минимум три контрольных сценария с ожидаемым/фактическим результатом и статусом:
1. Штатный: запуск потока, предсказание, сортировка, просмотр карточки.
2. Граничный: допустимый нетипичный вход и/или расхождение двух моделей; сервис корректно показывает результат без утверждения о его достоверности.
3. Ошибочный: некорректный запрос или недоступный API; понятная ошибка и отсутствие зависания интерфейса.

Docker содержит сервис и нужные runtime-зависимости. Обучение выполняется отдельно на Mac в изолированном окружении. Сохранённые доверенные артефакты включаем в образ либо подключаем документированным read-only volume. MLflow не является зависимостью работающего inference-сервиса; его UI запускается отдельно для исследования.
